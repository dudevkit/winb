## 2. Root causes (ordered by impact)

### R1 - Client latency: ~2.8 s per call is 97% overhead (P0)

Measured median round trip for `winb "echo hi"`: **2.81 s**. Direct HTTP POST to the same endpoint:
**22 ms**. From inside the PC: **131 ms**.

Cause: the client shells out to `jq` **6 times per call** (1x payload build, 5x response field parse).
On this gateway `jq` costs **451 ms per spawn** -> 2.7 s pure overhead.

```
jq -n .                       0.451 s
jq x6                         2.702 s
python3 -c pass               0.227 s
curl /health                  0.041 s
server-side POST /run         0.131 s   (measured on the PC itself)
```

Fix: one `python3` process for build+parse (or a single `jq` call with a TSV template). Expected
2.81 s -> ~0.30 s per call (**9x**). Over 7.4k calls this is hours of wall-clock.

### R2 - stdin payload hard cap at ~75 KB, with cryptic error (P0)

`--stdin-file` base64-encodes into a jq command-line argument. Two limits collide:

* `jq --arg` hits `Argument list too long` at ~120 KB payload (proved at 120 KB: `jq: Argument list too long` then `Server Error: Command is required`)
* `express.json()` default limit is 100 kb, so a 90 KB file (120 KB base64) returns HTML 413, which the client reports as `parse error: Invalid numeric literal at line 1, column 10`

Effective usable payload: **~75 KB**. Any larger script silently degrades into a jq parse error with
exit code 0 in some paths.

Fix: `curl --data-binary @-` with the payload on stdin, and `express.json({ limit: '64mb' })`.

### R3 - Timeout does not kill the process tree, and can hang forever (P0)

`child.kill()` on Windows kills only `cmd.exe`. A grandchild keeps the stdout pipe open, so the
server's `'close'` event never fires and **the HTTP response is never sent**.

Reproduction: `winb -t 6 "python -m http.server 8899"` -> the client hung for the full 300 s terminal
budget, and `PID 28744 python @ :::8899` was still listening afterwards. Killed manually.

Consequence: every long-running command that spawns a child (servers, browsers, node, ffmpeg) can
wedge an agent turn, and leaks processes on the PC.

Fix: on timeout use `taskkill /pid <pid> /f /t`; listen on `'exit'` not `'close'`; add a response
deadline; add client-side `curl --max-time`.

### R3b - A spawn error kills the whole server, not just the request (P0)

Reproduced twice today, deliberately the second time:

```
winb -w "F:\winb-nonexistent-dir" "echo hi"
Error: server: spawn C:\Windows\system32\cmd.exe ENOENT
```

`server.log`:
```
[EXEC] export... (cwd: F:\winb-nonexistent-dir)
[HTTP] POST /run - 500
Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client
    at ChildProcess.<anonymous> (api.js:184:17)   <- res.json in the 'close' handler
Node.js v24.19.0
[WATCHDOG] 08:23:29 - server down; restarting node
```

`child.on('error')` answers 500, then `child.on('close')` answers again on the same response, the
throw is uncaught and **the node process exits**. Every session loses PC access for ~15-20 s until
`watchdog.ps1` respawns it (verified: PID 39524 -> 9936, uptime reset to 0).

Consequence beyond the bug itself: a single typo in `-w` in any past session took down the bridge for
everyone, which is a plausible source of historical "winb is unresponsive" episodes.

Client-side mitigation shipped today: the error is now explained by name, and a following call waits
out the watchdog respawn instead of failing (measured: next call succeeded after 13.4 s).

Server fix (Phase 2): register handlers with `.once`, guard with `res.headersSent`, and validate the
workdir before spawning.

### R4 - PowerShell path destroys non-ASCII output (P0)

UTF-8 file `Invoice ready - 12 items, 50% done ✓ é`:

| Path | Bytes returned |
|---|---|
| `winb "type file"` (cmd) | `e2 9c 93` - intact |
| `winb -p "Get-Content file"` | `ef bf bd` - **U+FFFD replacement** |
| `winb -p "[Console]::OutputEncoding=[Text.Encoding]::UTF8; ..."` | `e2 9c 93` - intact |

105 historical results carried encoding damage (`charmap`, `codec`, `\ufffd`).

Fix: server prepends `$OutputEncoding = [Console]::OutputEncoding = [Text.Encoding]::UTF8` when
`powershell: true`, and `chcp 65001` for the cmd path. Buffer as `Buffer`, never `data.toString()`
without validation.

### R5 - Multi-line cmd commands silently run only the first line (P0)

```
winb "echo line1
echo line2"     ->  "line1"      (exit 0, line2 silently dropped)
winb -p "Write-Host a
Write-Host b"   ->  "a\nb"       (correct)
```

Silent partial execution is the worst class of bug for an agent: the model believes both lines ran.

Fix: detect newlines in the cmd path and materialize a temp `.cmd` file, or reject with a clear error
telling the caller to use `-p` or a script file.

### R6 - NUL bytes dropped with a bash warning (P1)

`winb -p "[Console]::Out.Write('A'+[char]0+'B')"` -> `bash: warning: command substitution: ignored null byte in input`.
Any binary-ish output (`type` on a binary, encrypted blobs, UTF-16 files) is truncated at the first NUL.

Fix: never round-trip stdout through `$(...)`. Stream the response body to a temp file and `cat` it,
or render as base64 when `--binary`.

### R7 - Default cwd is the server directory (P1)

93% of calls omit `-w`, so they execute in `winb-server`. Evidence of pollution in
that folder: files literally named `5000` and `document.body.innerText.slice(0`.

The `--admin` SSH path uses a different default (user home), so the same command behaves differently
per transport.

Fix: default cwd `<scratch dir>` (auto-created), documented; `--admin` uses the same
default; `cd` semantics returned in every response (`cwd_before`/`cwd_after`).

### R8 - Server API is unauthenticated on 0.0.0.0:5110 (P0, security)

`app.listen(PORT)` with no token check. Any host on the LAN gets arbitrary code execution on the PC
that holds the browser profiles and wallet extensions.

Fix: bearer token from a file, bind `127.0.0.1`, reach it through an SSH tunnel or Tailscale; IP
allowlist as fallback.

### R9 - No output cap, no truncation flag, no persistence (P1)

stdout is accumulated in memory and JSON-encoded (2x memory), with no cap. 5 MB round trip works but
takes 7.8 s. Background logs are a 500-line in-memory ring; a reload/restart loses them. `server.log`
is **13 MB with no rotation** (grew 865 KB on the audit day alone).

Fix: cap at 2 MB per stream with `truncated: true` + full output saved to `%TEMP%` and its path
returned; persist job records to `jobs.json`; rotate `server.log` at 10 MB, keep 3.

### R10 - Dead code and drift (P2)

`routes.js` is a stale copy of `api.js` with no base64/env support - never loaded, but it invites edits
that do nothing. Root also holds stray artifacts (`5000`, `document.body.innerText.slice(0`,
`progress.json`).

## 3. Upgrade plan

### L1 - Client (`the winb CLI`, rewrite as `winb` v2)

| Change | Impact |
|---|---|
| single-process payload build + parse (python3, no jq) | 2.81 s -> ~0.30 s |
| payload via `curl --data-binary @-` | removes 75 KB cap and ARG_MAX class of bugs |
| `curl --max-time` = `-t` + 10s, `--connect-timeout 5`, 2 retries on connect failure | no infinite hangs |
| stdout streamed to temp file, never `$(...)` | survives NUL bytes and trailing newlines |
| `--json` flag: pass raw server JSON through | agents get typed fields, no lossy flattening |
| `--out <path>`: save full stdout locally, print a summary | big output without context blowup |
| auto-`--raw` whenever the command contains quotes/newlines | deletes the `--raw` decision from the caller |
| `winb put <local> <remote>` / `winb get <remote> <local>` | replaces the 48% `%TEMP%` workaround |
| `winb doctor` | health + latency breakdown + cwd + codepage + PS version + ports |

### L2 - Server (`winb-server` v1.3)

| Change | Impact |
|---|---|
| token auth + bind 127.0.0.1 | closes LAN RCE |
| UTF-8 forced for both shells, `Buffer` transport | no more U+FFFD / cp437 damage |
| timeout kills the tree (`taskkill /t`), respond on `'exit'` | no wedged requests, no leaked python/node |
| multi-line cmd -> temp `.cmd` file | no silent first-line-only execution |
| output cap 2 MB + `truncated` + `%TEMP%` spill path | bounded memory, nothing lost |
| `express.json({limit:'64mb'})` | file payloads above 75 KB work |
| default cwd `<scratch dir>` | kills the pollution class |
| job records persisted + `/jobs` list | background state survives reload |
| log rotation + request id per call | diagnosable without a 13 MB blob |
| delete `routes.js`, clean stray files | no false edit targets |

### L3 - Agent bridge contract (the actual purpose of winb)

Right now winb is a shell RPC, so every agent re-derives device facts with shell probes (`dir`,
`tasklist`, `where python`, `--port`). That is why 71% of calls are exact repeats and why 48% of calls
first write a helper script somewhere.

Proposed capability layer:

1. `GET /manifest` - one call returns everything an agent needs before acting:
   `os`, `hostname`, `cwd_default`, `shells`, `python`/`node`/`git` versions + paths, `drives` + free
   space, `allowed_roots`, `max_payload`, `default_timeout`, `capabilities: [exec, put, get, fs, proc, port, open_url, manifest]`, `version`.
2. Typed operations, each returning the same envelope
   `{ok, exit_code, status, duration_ms, stdout, stderr, truncated, cwd_before, cwd_after, host, request_id}`:
   - `exec` (current `/run`, hardened)
   - `fs.stat` / `fs.list` / `fs.read` / `fs.write` / `fs.move` / `fs.rm` (guarded by `allowed_roots`)
   - `proc.list` / `proc.kill` (tree) / `proc.logs`
   - `port.check`, `net.whois`
   - `open_url`
3. `put`/`get` as first-class transfer so agents stop depending on the SMB mount being alive (the
   mount drops when the PC sleeps - a recurring failure in past sessions).
4. Optional sticky session: `winb sh --id main` keeps cwd + env between calls, so an agent does not
   have to re-establish context each time.

### Phasing

| Phase | Content | State |
|---|---|---|
| 1 | client v2 (latency, `--json`, `--out`, `--cmd-file`, max-time, put/get, doctor) | **done 2026-11-01** |
| 2 | server v1.3 (token auth, forced UTF-8, tree-kill, multi-line cmd, output cap, scratch cwd, job persistence, log rotation, 64 mb body) | **done 2026-11-01** |
| 3 | typed operations (`fs.*`, `proc.*`) + `/manifest` | `/manifest` done; typed ops still open |
| 4 | sticky sessions (`winb sh --id`) | open |
| 5 | skill updated with the new contract and pitfalls | **done** |

### Acceptance tests (must pass before each phase is called done)

1. `winb "echo hi"` median < 0.5 s over 5 runs.
2. `winb -p "[Console]::Out.Write([char]0x2713)"` returns `e2 9c 93`.
3. 300 KB file via `put`/`--stdin-file` arrives byte-identical (`sha256` compare).
4. `winb -t 5 "python -m http.server 8899"` returns within ~6 s, exit 124, and port 8899 is closed afterwards.
4b. `winb -w "F:\nonexistent" "echo hi"` returns a clear error and the server PID is unchanged.
5. `winb "echo a\necho b"` either runs both lines or fails loudly (never silently runs one).
6. `POST /run` without the token returns 401; from another LAN host it is unreachable.
7. `winb --out /tmp/x.log "type bigfile"` returns a short summary and the file matches byte count.

## 3b. Result - Phase 1 + Phase 2 shipped (2026-11-01)

Acceptance suite `verify_phase2.py`: **13/13 passed**. Client regression suite
`verify_equivalence.py`: matrix green, 7/7 fix checks pass.

| Acceptance test | Result |
|---|---|
| 1 latency | 0.341 s median (was 2.84 s) |
| 2 UTF-8 through PowerShell | `e29c93` (was `efbfbd`) |
| 3 300 KB upload, sha256 verified | pass |
| 4 timeout bounded + process tree killed | 5.4 s, port free afterwards (was: hang forever) |
| 5 multi-line cmd | both lines run (was: first line only, exit 0) |
| 6 auth | `/run` 401, `/reload` 401, `/health` 200, token 200 |
| 7 `--out` byte exact | 250000 bytes |
| 8 bad workdir | clean 400, server PID unchanged (was: whole server crash) |
| 9 NUL bytes | preserved |
| 10 200 KB stdin | 0.4 s (was: rejected at ~75 KB) |
| 11 `/manifest` | host, tools, drives, limits |
| 12 background records survive reload | pass |
| 13 output cap + spill | 3 MB request truncated at 2 MB with a spill path |

Bugs found and fixed during Phase 2 beyond the audit list:

* **stdin pipe was never closed.** The child's stdin stayed open, so any command that reads
  stdin blocked forever. A pipeline like `findstr x | find /c y` was enough to hang a request
  for good (reproduced: 400 s hang). Fixed by piping the body through `child.stdin` and always
  ending it; the old `cmd < file` redirect also bound to the wrong pipeline element.
* **A missing workdir crashed the entire server** (R3b above).
* **`/reload` was unreachable-proof but unprotected.** Auth now lives in `server.js` before the
  reload route, so it covers that endpoint too.

New facts an agent must know after this phase:

* Requests from the LAN require `Authorization: Bearer <token>`. Token lives at
  `winb-server\.token` (PC) and `~/.winb-token` (gateway); the v2 client
  reads it automatically. Loopback is trusted so the watchdog keeps working.
  **Deleting the token file disables auth (fail-open)** - that is the recovery hatch if a token is
  ever lost, and the reason the file must not be removed casually.
* Body limit is 64 mb, so `--stdin-file` handles up to 40 MB and `winb put` chunk size is 4 MB.
* `server.log` is rotated manually during a restart window (the launcher holds the handle, so an
  in-process rename fails on Windows). One generation is kept as `server.log.1`.

## 4. What was NOT found to be broken

Evidence against these common assumptions:

* Large stdout is fine: 200 KB and 5 MB both arrive byte-complete (5 MB took 7.8 s).
* Exit code fidelity is fine: `exit 7` -> 7, `cmd /c exit 3` -> 3, timeout -> 124.
* stdout/stderr separation is fine at the CLI boundary.
* Hot reload, port check, open-url, job list/kill all behave as documented.
